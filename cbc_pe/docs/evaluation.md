# CNN evaluation workflow

This document describes how CNN prediction results should be evaluated in the `cbc_pe` project.

The current goal is to compare candidate CNN architectures trained on the 100k HDF5 dataset using an 80/20 train/validation split.

Final conformal evaluation requires a separate calibration and test split and should not be reported using the current 80/20 architecture-selection split.

## Current status

CNN evaluation is currently notebook-based.

The main notebook is:

```text
cbc_pe/notebooks/03_cnn_evaluation_hdf5_demo.ipynb
```

The notebook loads prediction and embedding files generated by:

```text
cbc_pe/scripts/train_cnn_hdf5.py
```

A future script should be added:

```text
cbc_pe/scripts/evaluate_cnn.py
```

## Input files

The evaluation notebook expects a prediction file generated during training, typically stored under:

```text
<data_root>/results/
```

Typical filename pattern:

```text
*_predictions_embeddings.npz
```

This file may contain arrays such as:

```text
pred_train
y_train
emb_train
idx_train
pred_val
y_val
emb_val
idx_val
pred_cal
y_cal
emb_cal
idx_cal
pred_test
y_test
emb_test
idx_test
y_mean
y_std
label_names
available_splits
```

For the current 80/20 architecture-selection split, only `train` and `val` may be available.

For final conformal evaluation, `cal` and `test` should also be available.

## Standardized-space evaluation

The CNN is trained on standardized labels.

Standardized-space metrics are useful for comparing model optimization behavior because all output labels are on comparable numerical scales.

For each split, compute:

- MSE
- RMSE
- MAE
- bias
- residual standard deviation
- median absolute error
- R2 score

These metrics should be computed globally and per label.

## Physical-space evaluation

For physical interpretation, predictions should also be transformed back to physical units using:

```text
y_physical = y_standardized * y_std + y_mean
```

Physical-space metrics should be computed for each label:

```text
chirp_mass
total_mass
chi_eff
```

At minimum, report:

- RMSE
- MAE
- bias
- residual standard deviation
- median absolute error

Physical-space plots are often easier to interpret than standardized-space metrics.

## Diagnostic plots

Validation loss alone is not enough.

For each candidate model, inspect:

- prediction versus truth
- residual histograms
- residuals versus true physical parameters
- residuals versus predicted physical parameters
- absolute error versus SNR
- per-label error distributions
- train versus validation error gaps

Useful plots include:

```text
predicted chirp_mass vs true chirp_mass
predicted total_mass vs true total_mass
predicted chi_eff vs true chi_eff

residual chirp_mass vs true chirp_mass
residual total_mass vs true total_mass
residual chi_eff vs true chi_eff

absolute error vs network SNR
absolute error vs total_mass
absolute error vs chirp_mass
absolute error vs chi_eff
```

## Architecture comparison

During architecture selection, record results in:

```text
cbc_pe/docs/architecture_search.md
```

Do not compare models only by global validation loss.

A better comparison should include:

- best validation loss
- per-label validation RMSE
- per-label validation MAE
- per-label bias
- residual standard deviation
- train/validation gap
- visual residual structure
- failure modes in high-mass or low-SNR regions
- usefulness of embeddings for difficulty-based Mondrian analysis

## Model selection criteria

A candidate model is better only if it improves the overall behavior of the regression problem.

A small improvement in global validation loss is not enough if the model introduces:

- larger bias in one label
- worse tails
- unstable errors at high mass
- unstable errors at low SNR
- poor `chi_eff` behavior
- embeddings that are not useful for difficulty estimation
- overfitting visible through a train/validation gap

For this project, local residual behavior matters because Mondrian conformal intervals depend on the structure of the errors.

## Current architecture-selection split

The current 100k architecture-selection setup is:

```text
train = 80000
validation = 20000
calibration = 0
test = 0
```

This split is acceptable for comparing CNN architectures.

It is not acceptable for final Mondrian conformal reporting.

## Final evaluation split

After selecting the architecture, the final model should be trained and evaluated using a split such as:

```text
train = 70%
validation = 10%
calibration = 10%
test = 10%
```

The intended use is:

- `train`: fit CNN weights
- `validation`: early stopping and model selection
- `calibration`: conformal calibration
- `test`: final reporting

The calibration and test sets must not be used to choose the CNN architecture.

## Recommended workflow

```text
1. Train candidate CNN architectures on the 100k 80/20 split.
2. Save predictions and embeddings.
3. Evaluate validation metrics in standardized and physical space.
4. Inspect diagnostic plots.
5. Record results in docs/architecture_search.md.
6. Select a candidate architecture family.
7. Re-run the selected architecture with a 70/10/10/10 split.
8. Use calibration and test sets for Mondrian conformal analysis.
9. Scale to 500k or 1M only after the evaluation pipeline is stable.
```

## Warning

Do not report pseudo-calibration results from a validation split as final conformal results.

Validation-split debugging is acceptable for pipeline development, but final conformal claims require separate calibration and test sets.
